# パフォーマンス計測（ベースラインと各フェーズの結果）

生データ（JSON）は [`docs/perf/`](perf/) にあります（`baseline/`、`phase1/`、`phase3/`、`phase4/`、`final/`）。

## 全フェーズのまとめ（最終結果）

## 計測方法

```bash
npm start                                   # 別ターミナルで開発サーバーを起動
LOW='{"quality":"low","fovMode":"h"}'
npm run measure -- --profile desktop --settings "$LOW" --runs 3               # デスクトップ・初回訪問
npm run measure -- --profile desktop --runs 1                                  # デスクトップ・既定画質 (high)
npm run measure -- --profile desktop --settings "$LOW" --cache warm --seconds 5 # デスクトップ・2 回目の訪問
npm run measure -- --profile mobile  --settings "$LOW" --runs 1                # スマホ模擬
```

- **初回訪問**：何も入っていないブラウザプロファイルで開いたときの値です。
- **2 回目の訪問**：1 度読み込んで HTTP キャッシュが入った状態で、もう 1 度開いたときの値です。
- **スマホ模擬**：横向きの 844×390、DPR 3、タッチあり、CPU を 4 倍遅くして、通信は「Fast 4G」（9Mbps、遅延 60ms）です。
- URL は `?map=tidewater&autostart=60&autopilot` です。起動が終わるとそのまま試合が始まり、オートパイロットで 10 秒間プレイしたところを計測します。

### 注意：この計測環境について

- 計測したのは GPU のないクラウドのコンテナ（4 コア、15GB）です。WebGL は SwiftShader、つまり CPU によるソフトウェア描画で動いています。
- そのため、**fps と起動時間の絶対値は実機とはまったく違います**。GPU で処理する部分（シェーダーのコンパイル、テクスチャ生成、環境マップの生成など）が極端に遅くなるためです。数字の比較は、同じ環境で計測した前後の値どうしに限ってください。
- 環境に左右されずそのまま使える値は、**転送量**、**draw calls / 三角形数**、**ジオメトリとテクスチャの数**、**JS ヒープ**です。
- スマホの fps 目標（30fps 以上）と起動時間の目標（ミドルレンジ Android で 8 秒以内）は、実機か GPU のあるマシンで確認する必要があります。そのときも同じ `npm run measure` を使えます（Mac なら Chrome と GPU を使って計測します）。

## 結果

### 転送量（初回訪問）

どの条件でも同じ値です。

| 種類 | リクエスト数 | そのままのサイズ | brotli 圧縮後（推定） |
|---|---:|---:|---:|
| Script | 63 | 4,668 KB | 971 KB |
| Stylesheet | 2 | 226 KB | 34 KB |
| Image（ステージ画像 webp） | 1 | 146 KB | 137 KB |
| Font | 2 | 45 KB | 45 KB |
| Document / Fetch | 2 | 3 KB | 1 KB |
| **合計** | **70**（+ キャッシュから 2） | **5,088 KB** | **1,189 KB**（gzip なら 1,406 KB） |

- 開発サーバーは圧縮せずに配信します。「brotli 圧縮後」は、配信された各ファイルを手元で brotli（品質 11）で圧縮したサイズです。圧縮して配信する CDN（Cloudflare Pages）を使った場合に近い値になります。
- スクリプトの大部分は three.js（`three.core.js` 1.46MB と `three.module.js` 0.66MB）で、どちらも minify されていません。
- 「キャッシュから 2」はフォント 2 本です。`src/world/props.js` が別名の `FontFace` として同じファイルをもう 1 度読みに行っています。初回訪問では HTTP キャッシュから返るので容量は増えませんが、リクエストは余計に発生しています。

### 2 回目の訪問

| 項目 | 値 |
|---|---:|
| 転送量 | 8.4 KB（66 リクエスト。ほぼすべてが 304 の再検証） |
| bootMs | 56,785 ms（初回訪問より約 1.3 秒短いだけ） |

- 開発サーバーも本番（`_headers` の `max-age=0, must-revalidate`）も、モジュールを開くたびに再検証しています。そのため、2 回目の訪問でも約 66 往復の通信が発生します。スマホの遅延（60ms）では、この往復が効いてきます。
- 起動時間が初回とほとんど変わらないので、**起動時間の大部分はダウンロードではなく、手続き生成とシェーダーのコンパイル**に使われていることが分かります。Phase 3 で狙うべきところです。

### 起動時間（bootMs = ページを開いてからタイトル画面が出るまで）

| 条件 | bootMs | DOMContentLoaded | FCP |
|---|---:|---:|---:|
| デスクトップ low・初回（3 回の中央値） | **58,061 ms**（57,326〜59,433） | 283 ms | 2,808 ms |
| デスクトップ high・初回 | 84,279 ms | 220 ms | 2,612 ms |

| スマホ模擬 low・初回 | 60,328 ms | 3,863 ms | 5,628 ms |

#### 段階ごとの内訳（ms）

`bootMarks` は、ロード画面のラベルが切り替わった時刻です。下の表の各行は、**そのラベルが出るまでの間に行われた処理**にかかった時間です。

| ラベル（その前に行われる処理） | low 初回 | high 初回 | スマホ low |
|---|---:|---:|---:|
| Mixing ink…（メニューと HUD のモジュール読み込み） | 55 | 56 | 599 |
| Building the plaza…（レンダラー作成、キャラクター・FX・環境・音声のモジュール読み込み） | 142 | 127 | 1,741 |
| Filling the harbor…（壁画テクスチャ、テクスチャライブラリ生成、プロップ、レベル、ライトマップ、インクアトラス、ナビ） | 9,122 | 22,401 | 10,631 |
| Teaching squids to swim…（`Environment`：空、PMREM 環境マップ、海、遠景） | 22,556 | 22,953 | 25,779 |
| Tuning the tentacles…（弾、FX、画面エフェクト、ショーケース） | 287 | 232 | 2,396 |
| Warming up…（パレット、イベント、アトラクトモードでのキャラクター生成） | 2,076 | 1,908 | 2,120 |
| Warming up…（エフェクトのウォームアップ） | 209 | 140 | 575 |
| Ready!（全シェーダーのコンパイル `compileAsync` と 3 フレーム描画） | 23,013 | 35,774 | 15,939 |

- 時間がかかっているのは、上から「Environment の構築」「シェーダーのコンパイル」「テクスチャ／ワールド生成」の 3 つです。
- SwiftShader は `KHR_parallel_shader_compile` に対応していません。そのため、`compileAsync` がシェーダーを順番にコンパイルする処理として計測されています。
- スマホ模擬では CPU を 4 倍遅くしても、GPU 側の処理が多い段階（Environment、コンパイル）はあまり変わりません。一方、モジュール読み込みや JS だけで行う段階は 5〜10 倍遅くなります。

### 試合中（オートパイロット 10 秒）

| 項目 | デスクトップ low | デスクトップ high | スマホ模擬 low |
|---|---:|---:|---:|
| draw calls | 175 | 362 | 172 |
| 三角形数 | 約 905,000 | 約 1,850,000 | 約 932,000 |
| ジオメトリ / テクスチャ | 122 / 29 | 97 / 40 | 119 / 29 |
| JS ヒープ | 88 MB | 87 MB | 85 MB |
| sim（1 フレームのロジック処理） | 8.4 ms | 8.1 ms | **37.4 ms** |
| render（CPU 側の描画処理） | 277 ms | 930 ms | 119 ms |
| 平均 fps / 1% low（参考値。ソフトウェア描画なので実機とは比べられません） | 0.5 / 0.4 | 0.2 / 0.1 | 1.0 / 0.8 |

- **sim はスマホ模擬（CPU 4 倍遅延）で 37ms** です。30fps を出すには 1 フレームを 33ms 以内に収める必要があり、描画を入れる前にロジックだけで予算を超えています。
  - `main.js` は、フレームが 1/45 秒より遅いと物理を 2 回に分けて計算します。そのため、30fps の端末でもこの 2 回分の計算が発生します。
  - Phase 5 では、ボット・物理・ペイントの更新頻度や処理コストが最初の検討対象になります。
- low の画質でも三角形数は約 90 万あり、スマホには多めです。プロップと遠景の LOD や、描画しない範囲の調整を Phase 5 で検討します。

## 動作テスト（smoke）

- `npm run smoke`（デスクトップ）：Linux では low 画質・960×540 で実行します。
- `npm run smoke:mobile`：スマホ模擬で同じ確認をします。タッチ操作に対応するまで（Phase 2）は、起動して試合が進むことだけを確認します。
- 結果：どちらも成功しました（試合が `playing` まで進み、コンソールエラーなし）。この環境では 1 回に約 4 分かかります。

  - スマホ模擬：boot 61.9 秒、sim 45.5 ms、draw calls 185
  - どちらも警告は `KHR_parallel_shader_compile extension not supported`（SwiftShader に対応機能がないため）の 1 件だけです。

#### やったこと
- **modulepreload**：ロード画面に必要な 54 モジュールを `index.html` で先読みします（`tools/gen-preload.mjs` で生成し、`npm run check` で古くなっていないか確認します）。残りのモジュールは、ロード画面が出た直後に並行して読み込み始めます。
  - 全部を先読みすると、スマホ模擬で FCP が 5.6 秒から 6.4 秒に遅くなりました（帯域の取り合いのため）。そこで先読みの範囲をロード画面に必要なものだけに絞りました。
- **GPU の完了待ちをやめた**：テクスチャライブラリ生成の直後にあった 1 ピクセル読み戻し（GPU の処理が終わるまで待つ）をやめ、次の処理と並行して進むようにしました。
- **波のテクスチャ生成を高速化**：海の波テクスチャで、sin・cos を行と列ごとの表から合成するようにしました。出力は 1 バイトも変わらず、約 3 倍速くなりました（mobile のプロファイルで 576 → 164 ms）。
- **ミニマップを後回し**：ミニマップは試合で最初に使うときに作るようにし、起動時には作りません。
- **並列化**：壁画テクスチャとテクスチャライブラリを並行して生成します。
- **フォントの二重読み込みをなくした**：プロップの看板が、ページで読み込んだフォントをそのまま使うようにしました。
- **空の生成を画質に合わせた**：雲（2048×640）と遠景の反射キューブ（512²）の生成解像度を画質設定で変えられるようにしました（`QUALITY[*].bake`）。**low 画質だけ半分**にしています。見た目の差は、同じカメラ位置で撮り比べてもほぼ分かりません。

#### 注意
- Environment の段階が大きく縮んだ理由のほとんどは、雲の生成を半分の解像度にしたことです。ソフトウェア描画ではフル解像度の雲の生成に約 14 秒かかっていました。**実機の GPU では 0.1〜1 秒程度の処理**なので、実機で縮む時間はこの表よりずっと小さくなります。また、high 以上の画質は変えていません。
- 「Warming up…」が増えているのは、GPU を待つタイミングがこの段階に移ったためです（1 ピクセル読み戻しをやめたことによる移動）。
- 残りで最も大きいのは「Ready!」段階のシェーダーコンパイルです。起動時点で 121 個のプログラムがあり、多くは `MeshPhysicalMaterial` の `onBeforeCompile` の違いによる別プログラムです。これを減らすにはプロップやキャラクターのマテリアル構成を見直す必要があるため、Phase 5（mobile 向け画質プリセット）で扱います。
- 2 回目以降の訪問を速くする Service Worker と、キャッシュのヘッダ（ハッシュ付きファイル名 + immutable）は、ビルドでファイル名にハッシュを付ける Phase 4 でまとめて行います。
- ツール：`tools/profile-boot.mjs` を追加しました。起動中の CPU プロファイルと、`--shaders` を付けるとプログラムごとのコンパイル・リンク時間を出力します。

- bootMs は変わりません。起動時間の大半は GPU 側の処理（ソフトウェア描画でのシェーダーコンパイルと生成処理）で、ダウンロード量ではないためです。この日のマシンは Phase 3 計測時より約 1.6 秒遅く、開発ツリーも 42.9 秒でした。

#### やったこと
- **esbuild でバンドル**（`tools/build.mjs`）：`src/main.js` から 1 本にまとめて minify し、動的 `import()` ごとにチャンクへ分割します（27 チャンク）。ファイル名には内容のハッシュを付けます。開発時はこれまでどおりビルドなしで動きます。
  - three.js の tree-shaking はほとんど効きません。ゲームが WebGL レンダラーのほぼ全体を使い、GLSL のチャンクが大半を占めるためです（`src/` のモジュール単位で解決する方法も試しましたが、7 KB 大きくなりました）。
  - `main.js` の動的 import はパス文字列の変数をやめ、リテラルの `import()` にしました（バンドラーが分割できるように）。
- **ページに必要なものだけ先読み**：dist の `index.html` は、ロード画面までに必要な 16 チャンクだけを `modulepreload` します。
- **Service Worker**（`sw.js`、ビルドで生成）：ハッシュ付きのバンドルとアセットはキャッシュ優先、ページはネットワーク優先です。ビルドごとにキャッシュ名が変わり、古いキャッシュは削除します。2 回目以降の訪問とオフラインでの起動はキャッシュから行います。日本語フォントは最初に使ったときにキャッシュします（英語だけで遊ぶ人はダウンロードしません）。
- **キャッシュ用ヘッダ**（`dist/_headers`、Cloudflare Pages）：`/js/app/*` と `/styles/*` は 1 年・immutable、`/assets/*` は 1 日、ページと `sw.js` は毎回確認します。`tools/release-pages.sh` はこのファイルを使います。
- **ライトマップを WebP に**（`tools/lightmaps-webp.py`）：焼き込み AO（グレースケール）を WebP q92 にします（合計 355 KB → 76 KB）。PNG との差は平均 0.1〜0.4/255 で、4 段階以上ずれる画素は 0.2% ほど（チャートの境目のみ）です。リポジトリには可逆の PNG を残し、変換はビルド時だけ行います。
- **日本語フォントのサブセットを小さく**：全角英数（U+FF01〜FF9F）を丸ごと入れるのをやめ、かな・記号と、訳文で使う文字だけにしました（178 KB → 165 KB）。
- **ステージ画像の読み込みを必要な分だけに**：メインメニューで、6 枚の大きなステージ画像（1920px、合計 1.7 MB）とサムネイルを先読みしていました。これをサムネイル（合計 260 KB）だけにしました。大きな画像は、ステージ選択でそのステージを表示するときに読み込みます。画面が小さい端末（スマホを含む）では、新しく作った 1280px 版（`-md`、1 枚 85〜160 KB、`tools/stage-variants.py`）を使います。
  - この分は起動後のメインメニューで発生する転送なので、上の表（タイトル画面まで）には含まれていません。

#### 目標との関係
- 転送量 −50%（594 KB 以下）には届いていません（−24%）。
  - 差の主な理由は、日本語化で加えた日本語フォント（165 KB）です。フォントを除いた分は 735 KB で、ベースライン比で −38% です。
  - 残りの JS 634 KB のほとんどは、ゲームのコード（ジオメトリや GLSL を手続き的に生成する処理）と three.js 本体です。GLSL の空白やコメントを削る方法も試算しましたが、brotli 後で 15 KB（2%）しか減らないため、見送りました。
- 2 回目以降の訪問はネットワーク転送 0 になります。

### Phase 5（実行時の最適化）後

スマホ模擬（CPU 4 倍遅延）・low 画質・tidewater で計測しました。この環境はソフトウェア描画なので、fps は実機の目安になりません。そこで次の 3 つを指標にしました。

- **1 フレームの CPU 時間**：`npm run bench`（描画を除く 1 フレームの更新処理を 30fps の固定ステップで 240 フレーム回し、プロファイルを取る）。
- **シェーダーのプログラム数**：`tools/profile-boot.mjs --shaders`。
- **描画コール数と三角形数**。

| 項目 | Phase 4 後 | Phase 5 後 |
|---|---:|---:|
| 1 フレームの CPU（描画を除く、平均） | 42.7 ms | **25.2 ms（−41%）** |
| 同 中央値 / 95 パーセンタイル | 31.5 / 74.1 ms | 22.5 / 53.4 ms |
| うち `putImageData`（ミニマップ） | 11.6 ms | 0.8 ms |
| 起動時にコンパイルするシェーダー | 121 | **63（−48%）** |
| 試合中のシェーダーの合計 | 114 | 77 |
| 描画コール（うち影） | 206（71） | 185（49） |
| 三角形数 | 約 113 万 | 約 98 万 |
| ステージを切り替えるたびに増えるジオメトリ / テクスチャ | +9 / +3 | 0 / 0 |

#### やったこと
- **シェーダーの二重コンパイルをなくした**：起動時の `compileAsync` は、描画先が画面（キャンバス）の状態で呼ばれていました。一方、実際の描画は EffectComposer の HDR レンダーターゲット（ショーケースやテクスチャ生成も同様）に行われます。three.js はプログラムを「出力の色空間とトーンマッピング」ごとに分けて作るため、起動時には誰も使わない版を作り、最初のフレームで本物をもう一度同期コンパイルしていました。`compileForTarget()`（`src/core/ctx.js`）で、実際の描画先を指定してコンパイルするようにしました。
  - ソフトウェア描画（ANGLE）ではプログラムを初めて使うときにコンパイルするため、この環境での起動時間はほとんど変わりません。
  - 実機（`KHR_parallel_shader_compile` あり）ではすべてのプログラムを先にコンパイルします。起動時のコンパイル量が約半分になるのは、実機のほうです。
- **HUD の強制レイアウトをなくした**：フレームの途中で `innerWidth` / `innerHeight` / `clientWidth` を読むと、その前に HUD が DOM を書き換えていた場合、ブラウザが同期レイアウトをやり直します。
  - 画面サイズは resize イベントで更新する `VIEW` から読むようにしました。
  - インクタンクの大きさは `ResizeObserver` で受け取るようにしました。
- **ミニマップを画面の大きさに合わせた（low のみ）**：これまでは 7 px/m 固定で 350×616 px の画像を 0.15 秒ごとに作り直していました。これを、画面の隅に表示される大きさに合わせて作るようにしました（スマホや 1080p では 4 px/m）。
  - 画素数が 1/3 になり、`putImageData` はほぼ無くなりました（小さいキャンバスは CPU 側で処理されるため）。
  - 影の長さは、画素の大きさが変わってもメートル単位で同じになるようにしました。
- **遠くのキャラクターの影を省略（low のみ）**：カメラから 20 m 以上離れたキャラクターは影を落としません。自分のキャラクターは常に影を落とします。1 体あたり約 37,000 三角形・5 描画コールを削れ、1024 の影マップでは遠くの影は数ピクセルしかありません。
- **スマホ・タブレットの初回起動は low 画質**：タッチが主な入力の端末（`(hover: none) and (pointer: coarse)`）では、画質を保存したことがない場合だけ low にします。ユーザーが選んだ画質は上書きしません。
- **動的解像度をスマホ向けに**：スマホ・タブレットでは 30fps を目標にします。
  - 約 32fps を下回ると解像度を下げます（下限は 0.75 から 0.5 に）。
  - 50fps を超えると解像度を戻します。
  - 半分の解像度でも 25fps 未満が 12 秒続いたら、「動作が重くなっています。設定で『グラフィック品質』を下げると軽くなります」と 1 回だけ表示します（low 以外のとき）。
- **ステージ切り替え時の解放漏れを直した**：飾り（スポーン台・街灯・ヤシ・旗）のジオメトリとマテリアル、そのキャンバステクスチャ 2 枚、ライトマップが解放されていませんでした。3 ステージを 2 周しても、ジオメトリとテクスチャの数が増えなくなりました。
- **ツール**：`npm run bench`（`tools/bench-frame.mjs`、`--render` を付けると描画込み）を追加しました。`tools/profile-boot.mjs --match 10` で、試合中の CPU プロファイルも取れます。

#### 確認
- デスクトップ high の見た目：同じカメラ位置の静止画を Phase 4 と比べました。違いは UI のアニメーションと、ボットが塗ったインクの位置だけでした。high / ultra に効く変更は、表示結果を変えないもの（コンパイルの描画先、レイアウトの読み方、解放漏れ）だけです。

#### やらなかったこと・マスタープロンプトとの違い
- **mobile プリセットは追加していません**。提案していた内容（pixelRatio 1.0、影 1024、MSAA なし、ブルーム・AO なし、paintAtlas 2048、パーティクル 0.35）は、既存の low（pixelRatio 0.75、影 1024、MSAA なし、ブルーム・AO なし、paintAtlas 2048、パーティクル 0.4、空の生成は半分）とほぼ同じです。そこで、スマホは low で始め、上の軽量化を low に入れました。
- **MeshPhysical を Standard に置き換える案は見送り**：二重コンパイルをなくしたことで、同じ見た目のプログラムの重複はなくなりました（重複ゼロを確認）。残りのプログラムはそれぞれ見た目が違うため、減らすには見た目を変える必要があります。
- **キャラクターのポーズ計算・ボット・ペイント**：1 フレームあたり、ポーズ計算は合計約 3 ms、ボットは 0.4 ms、ペイントは 1 ms 前後でした（4 倍遅延時）。遠くのキャラクターの更新を間引くとカクつきが見えるので、手を入れていません。
- 音楽の音符ごとの Web Audio ノード生成も、フレームあたり約 1.5 ms（4 倍遅延時）かかっています。これは作曲エンジンの作りに関わるため、今回は変えていません。
- **実機での fps は未確認**です（この環境に実機がないため）。

### 60fps 化とタブのクラッシュ対策（2026-10）

スマホ模擬（844×390、DPR 3、タッチ）・画質「省電力」・tidewater で計測しました。目的は、ミドルスペックのスマホで熱くならずに 60fps を保つことと、iPhone でブラウザのタブがたまに落ちる問題を減らすことです。

**1 フレームの CPU 時間**（描画を除く、CPU 4 倍遅延、1/60 秒の固定ステップで 240 フレーム）
`npm run bench -- --map tidewater --seed N --settle 15 --fps 60` を、種 7・11・13 で変更前と変更後に回した平均です。試合の展開で ±20% ほどぶれます。

| 項目 | 変更前 | 変更後 |
|---|---:|---:|
| 平均 | 16.9 ms | **15.2 ms（−10%）** |
| 中央値 | 15.3 ms | 13.5 ms（−12%） |
| 95 パーセンタイル | 38.9 ms | 33.4 ms（−14%） |
| Web Audio のノード生成（20 秒あたり） | 3,652 | **1,346（−63%）** |
| うち発振器 | 1,194 | 257（−78%） |

- この計測には、描画と、音声スレッドの負荷が入りません。今回の変更の多く（効果音・BGM の録音、影のフィルタ、インクの乾き）は、主に音声スレッドと GPU を軽くするものです。

**メモリ**（`npm run memory`、タイトル → 3 ステージを昼・夕方で 1 回ずつ）

| 項目 | 変更前 | 変更後 |
|---|---:|---:|
| GPU（テクスチャ・レンダーバッファ・バッファ） | 189〜249 MB | **164〜197 MB** |
| canvas | 34〜52 MB | **2〜4 MB** |
| JS ヒープ（6 試合後） | 143 MB | 137 MB |
| ジオメトリ数（6 試合後） | 213 | 200 |
| JS ヒープの増加（3 試合あたり、ヒープスナップショットの差） | 10.0 MB | **3.1 MB** |
| 前の試合から残り続ける `Character`（3 試合あたり） | 24 体 | **0 体** |

- 表の上 4 行は、FxHooks の修正の前に測った値です。JS ヒープは 6 試合で 137 MB でしたが、12 試合では 1 試合あたり約 4 MB ずつ増え続けました。ヒープスナップショットでたどると、`FxHooks` がキャラクターごとの状態を `Map` で持っていて、終わった試合の 8 体を（骨・メッシュごと）解放させていませんでした。`WeakMap` にしたあとは、残り続ける `Character` は 0 体です。残る 3.1 MB は配列のデータで、髪や効果音・BGM の録音のキャッシュが上限まで埋まる分です。

#### やったこと
- **効果音を録音して使い回す**：これまでは鳴らすたびに、約 25 個のノード（発振器・ノイズ・フィルター・エンベロープ）を組み立てて合成していました。最初の再生時に、裏で 3 テイクを `OfflineAudioContext` で録音し、以降は 1 つの `AudioBufferSource` で鳴らします。距離のフィルター、パンナー、リバーブは今まで通りで、ピッチの揺らぎは再生速度で付けます。長い音（1.6 秒超）、ピッチが ±20% を超える再生、ループは、今まで通りその場で合成します。
- **BGM の短い音符を録音して使い回す**：1.2 秒までの音符（ドラム、ベース、リード、コード、アルペジオ）を、楽器・音高・長さ・強さ（0.1 刻み）ごとに録音します。長いパッドやクラッシュ、開いたハイハット（次のハイハットで止める必要がある）は、その場で合成します。録音の上限は、効果音 8 MB、BGM 12 MB です。
- **キャラクターのポーズ計算を時間で間引く**：画面外は 1 秒 20 回まで、15 m 以上離れたキャラクターは 1 秒 30 回までです。30fps では今まで通り毎フレーム計算するので、60fps にしても、離れたキャラクターの計算量は増えません。
- **ミニマップ**：インクが変わった範囲（`PaintSystem.takeDirty`）だけを描き直します。スマホでは、マーカーなどの重ね描きを 1 秒 30 回までにしました。
- **毎フレームの `matchMedia('(prefers-reduced-motion)').matches` をやめた**：読むたびにメディアクエリを評価し直していました。
- **GPU（スマホ）**：
  - インクを乾かす処理（アトラス全体の書き換え）を、1 秒 20 回から 5 回にしました。1 回の量を 4 倍にしたので、乾く速さは同じです。
  - 影のふちのフィルタを、9 回から 4 回の読み取りにしました。比較つきの補間で、ほぼ同じ範囲をぼかします。
  - 20 m 以上離れたキャラクターの影の省略を、すべての画質で行います。
- **メモリ**：
  - 髪のジオメトリのキャッシュ（髪型 × 帽子 × 眉の組み合わせ、数百通り）が、際限なく増えていました。参照カウントを入れ、使われていない髪型は新しい 12 個まで残して破棄します。
  - 小物アトラスと壁画の 2048² の canvas（各 16 MB）は、最後に GPU へ送ったあと 1×1 に縮めます。
  - 小物の部品テンプレートは、ステージを作り終えたら捨てます。
  - スマホでは、ショーケース（ロッカー・リザルト）のキーライトの影を 2048 から 1024 にしました。閉じたら、影マップと全画面の描画先を解放します。
  - WebGL コンテキストが失われたら復旧を求め、戻ったらページを読み込み直します（失われた描画先や、縮めた canvas は戻せないため）。
  - `FxHooks` の、キャラクターごとの状態（`st`、`flickT`）を `WeakMap` にしました。`Map` だったため、終わった試合のキャラクターが、セッションのあいだずっと残っていました。
- **60fps**：スマホの既定のフレームレート上限を 60 にしました。以前の既定値の 30 のままの人も、一度だけ 60 に移します（`q3`）。解像度を 0.75 倍まで下げても 45fps 未満が 12 秒続くときは、30fps の上限を一度だけ勧めます。メニュー中の 20fps 制限は、スマホではどの画質でも行います。
- **ツール**：`npm run memory`（`tools/measure-memory.mjs`）を追加しました。`npm run bench` に `--seed` と `--settle` を足し、ウォームアップのあとに少し待つようにしました（録音が済んでから測るため）。

#### 確認
- `npm run check`、`npm run i18n`、`npm run smoke`、`npm run smoke:mobile`、`npm run test:touch`（15 / 15）、`npm run build`
- 2048² 以上のテクスチャの数を、6 試合（3 ステージ × 昼・夕方）のあいだ追いかけました。4〜7 枚のまま増えません。

#### やらなかったこと
- **キャラクターの LOD**：1 体約 34,000 三角形（服 17,500、体 10,400、髪 5,500）のままです。服と体は、細かい部品をそれぞれの分割数で作っているので、まとめて減らすと形が崩れるおそれがあります。
- **一時的なメモリ確保**：1 フレームに約 340 KB あります（髪の揺れ、ポーズ、レイキャストなど）。大半は計算途中の数値で、減らすには大きな書き換えが必要です。
- **実機での fps は未確認**です。CPU 4 倍遅延の模擬でも、描画を除いて 1 フレーム 13〜15 ms かかるので、本当のミドルレンジの端末では、60fps はぎりぎりです。iPhone 17 の CPU は、この模擬よりずっと速いです。
